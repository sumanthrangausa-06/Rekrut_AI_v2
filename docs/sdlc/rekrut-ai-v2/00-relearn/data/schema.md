**No live-DB introspection was possible from the build VM** — the VM cannot reach the production database. This document is therefore **migration-derived truth, not live-DB truth**. Drift between the migrations and the live database is **NOT VERIFIED** and must be assumed possible: there is positive evidence of drift (indexes in `070_analytics_indexes.js:55,69` target tables — `pipeline_stages`, `company_engagement_metrics` — that no migration creates; that migration swallows the error per-index in a try/catch at `070_analytics_indexes.js:101-104`, so those tables may exist only in the live DB, or nowhere).

**How to read an entry.** `table — src <file:line of first CREATE>. Cols: name TYPE [annotations]. Constraints: … Indexes: <names only>.`
Annotations: `[added <file:line>]` = column arrived via a later `ALTER TABLE … ADD COLUMN`; `-> TYPE x [<file:line>]` = a later `ALTER COLUMN … TYPE` (almost always the `p2_schema_hardening.sql` VARCHAR→TEXT sweep, which is conditional on the column existing); `re-add:` = a later `ADD COLUMN IF NOT EXISTS` that was a no-op. Inline `PRIMARY KEY` / `UNIQUE` / `REFERENCES … ON DELETE …` inside a column definition are part of that column's definition. Where the extractor could not resolve a final type/default unambiguously, the entry says **NOT VERIFIED** — nothing in this document is guessed.
