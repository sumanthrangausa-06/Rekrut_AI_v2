## What was built

The dark chassis only — no signal logic (#808), no IP capture (#815), no UI (#809, not built dark either), no external calls of any kind, nothing recruiter- or candidate-visible, no ranking/filter input.

- **Migration `260_threat_intel_checks.js`** (JS convention, `name` field set): table per STOP 1 §3a — `job_application_id` FK to `job_applications(id)` with **no cascade action** (the parent row is retained as a skeleton under #780, so a cascade could never fire, and an uncounted cascade would be an unprovable erasure); `company_id` denormalised from the application row at record time; `source`; `severity` with equality CHECK (`severity = 'info'` — raising the cap requires a migration); `subject_fingerprint` nullable with format CHECK `subject_fingerprint ~ '^[0-9a-f]{64}$'` (security C3); `signal_payload` JSONB; `sources_checked`/`sources_failed`; `checked_at`; `created_at`; indexes on `job_application_id` and `(company_id, subject_fingerprint)`. Idempotent (`IF NOT EXISTS` throughout), run inside migrate.js's per-migration transaction. One recorded refinement of §3a: `company_id` is **nullable** — privacy C3 requires subject-less provenance rows to record (NULL fingerprint) on legacy NULL-company applications, which a NOT NULL column would make impossible; subject-bearing checks on such applications are refused at the app layer — and, after the PR-gate fix round (database F1, below), the same invariant is also encoded in the schema by the named CHECK `threat_intel_checks_siloed_fingerprint`.
- **`lib/threatIntelFlag.js`** — single reader of `THREAT_INTEL_ENABLED` (observerCaptureFlag pattern: exactly `'true'`, read fresh on every call, everything else OFF).
- **`lib/threatIntelChecks.js`** — exports **only** `recordCheck` (security C6: no read/lookup/compare export of any kind — no fingerprint oracle). `recordCheck` refuses with a coded error and zero writes when the flag is OFF — **before any secret access** (security C2) and before any DB access. Company scope is derived from the application row on the caller's client, never caller-asserted (security C8). Provider registry is config shape only and **empty by default**; `source` and every `sources_checked`/`sources_failed` entry must be registry keys; the only provider exercised anywhere is an injectable `internal_test` provider performing no I/O. No logging anywhere in the module (security C6 / privacy C6 — errors carry codes + static text only).
  - **Crypto (STOP 1 §3b):** dedicated `THREAT_INTEL_HMAC_SECRET`, read lazily inside the fingerprint function only; unset or under 32 chars → coded `CONFIG_ERROR` hard-fail in every environment (r2FrameStore pattern — explicitly not biometricAudit's fallback pattern; a grep census in the test suite proves no fallback/default string exists, and the test secret is supplied via env only). Derivation: `companyKey = HMAC(secret, 'threat-intel:v1:company:' + companyId)`; `fingerprint = HMAC(companyKey, kind + ':' + normalisedValue)`, hex. `kind` validated `^[a-z][a-z0-9_-]*$` (security C5). The module header documents (security C7): the fingerprint is **pseudonymisation, not de-identification** — low-entropy values are reversible by recomputation to any secret holder; rotating the secret orphans all existing fingerprints (accepted for a dark chassis); and (privacy C5) rows recorded before #788 closes are never surfaced — any future release covers only post-determination checks, absent counsel's written clearance.
  - **Payload contract (security C4 + privacy C1):** `signal_payload` must be a plain object, ≤ 16 KiB serialised; keys at any depth screened token-wise against a raw-identifier denylist (ip, email, phone, name, ssn, address, dob, birth, passport, licence, card, iban, subject, value, username, password — erring wide); any string value equal to the raw subject (or its normalised form) is rejected.
  - **Privacy C3 (STOP 1 fail-soft OVERRIDDEN):** a subject supplied for an application whose `company_id` is NULL → coded refusal, zero writes. Subject-less rows may still record with a NULL fingerprint, with the case surfaced in the result (`companyId: null, siloed: false`).
- **Erasure wiring (`lib/erasureService.js`)** — in the #813 C2 position (immediately after the C2 block): explicit counted `DELETE FROM threat_intel_checks WHERE job_application_id = ANY($1)` over the inherited **#780 unheld application set**; result gains `threatIntelChecksDeleted` (rowCount) and `threatIntelRowsHeld` (one `COUNT` over the held set, issued only when that set is non-empty). **No new hold consult** is introduced (the block inherits the contained set — #1167-safe). Header comment documents the new family alongside the others, per the file's convention; JSDoc return shape updated.
- **Keep/erase registration** — Lex's two amended rows added **verbatim** to §2 (MUST ERASE) of `docs/sdlc/rekrut-ai-v2/00-relearn/data/erasure-keep-erase-table.md`: payload tier MUST ERASE (whole-row DELETE, C2 position, #780 unheld set, held rows survive whole and counted); audit-metadata tier MUST ERASE by default with **no MAY-KEEP line created**, no 90-day period adopted, no purge built, clock OPEN — counsel (#788).
- **DSAR follow-up (privacy C4)** — filed before this PR: **#1210** `[FOLLOW-UP] DSAR/export coverage for threat_intel_checks + candidate transparency` (labels story/follow-up/privacy). The DSAR export route uses a fixed user_id-keyed table list; `threat_intel_checks` has no user_id column and is NOT covered. Acceptable only while dark with no production rows. **HARD TRIGGER: #1210 BLOCKS setting THREAT_INTEL_ENABLED=true in any production environment** until export coverage + candidate transparency are built.

## Fix round — database gate condition F1 (PR #1211, 2026-10-15)

The database reviewer's PR-gate verdict on head `23e84c69` was **CLEAR WITH CONDITIONS** — one MEDIUM condition, **F1**: migration 260 must DB-encode the silo invariant the way its other guardrails are encoded. Nullable `company_id` was accepted (privacy C3 needs subject-less rows on legacy NULL-company applications), but the fingerprint-without-company state had to be impossible in the schema, not only refused in code.

- **Change (migration 260 amended in place — 260 is undeployed, no new migration):** table-level named constraint added to the `CREATE TABLE`: `CONSTRAINT threat_intel_checks_siloed_fingerprint CHECK (company_id IS NOT NULL OR subject_fingerprint IS NULL)` — a non-NULL fingerprint requires a company. The migration header now documents the DB encoding alongside the app-layer refusal. Migration remains idempotent (`IF NOT EXISTS` throughout, 258/259 pattern) and still runs clean through `migrate.js` on a fresh DB (see dry run below; fresh-DB catalog confirms the constraint: `threat_intel_checks_siloed_fingerprint CHECK ((company_id IS NOT NULL) OR (subject_fingerprint IS NULL))`).
- **Red-first order (honest record):** the source assertion was added FIRST to `server/__tests__/lib/threat-intel-severity.test.js` ("migration 260 encodes the silo CHECK: a non-NULL fingerprint requires a company (database F1)" — asserts the constraint name and the CHECK expression in the migration source), and run BEFORE the migration edit: **RED — 1 failed / 9 passed** (the new assertion failed on the absent CHECK). The migration was edited second; the suite then went green.
- **Suites after the fix:** threat-intel set **8/8 suites, 63/63 tests pass** (62 prior + the new F1 assertion); the two pinned erasure suites (`embeddings-erasure`, `dsar-dek-destruction`) **16/16 pass**.
- **Real-DB dry run re-run** (same shape as the original: scratch PG on 127.0.0.1:55433, fresh DB `threat807_dryrun` recreated, migrated to head including amended 260 **via the same disclosed scratch workaround** for the pre-existing p2 fresh-DB defect (#1149 family — views dropped in scratch only, migrate to head exit 0, views recreated from migrations 236–240; no repo migration changed), production-shape `erasePersonalData` in one BEGIN…COMMIT): **20/20 assertions passed** — all 18 prior assertions still pass, plus the two new F1 assertions: **(a) INSERT with `company_id` NULL + a valid-format fingerprint is REJECTED by the new CHECK** (error names `threat_intel_checks_siloed_fingerprint`); **(b) INSERT with `company_id` NULL + `subject_fingerprint` NULL is ACCEPTED** (the lawful subject-less provenance row).
