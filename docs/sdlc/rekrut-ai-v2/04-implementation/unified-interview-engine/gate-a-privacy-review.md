## Verdict — in plain words

**BLOCK. Do not take this package to Sumanth as approved. Rex must revise the design and the package returns for re-review.**

The dormant half of Rex's design is genuinely good. Moving audio subscription behind the capture gate (§2.3), strict-`true` flag parsing, per-chunk consent re-checks, fail-closed registration *as an intent*, AAD-bound envelope encryption, no reader, no report, no fallback scores, self-hosted-only ASR — that is the right shape, and several choices are stronger than the precedents they replace.

The package is blocked because the design, as written, approves more than dormancy. If someone flips one env var, the design as written would:

1. **Record real candidates on January's presence consent** — the capture gate re-uses `biometric_collection === true`, the exact consent-banking Lex's RL-01 forbids (P-1).
2. **Record any consented candidate, anywhere** — there is no cohort check, no synthetic/test-only guard, and no encoded re-entry checklist in the capture path. The flag flip *is* the activation, technically (P-2).
3. **Be able to leave an audio object in storage that nothing can ever find or delete** — the PUT-first registration order has a crash window with no registry row *and* no ledger row (P-3), and backups / replicas / object versions are never enumerated, so erasure provably does not reach every copy (P-4).

None of these require collecting a single byte today to be design defects. They are the activation path, written down, and approval would ratify them.

**Blocker count: 8** (P-1 to P-8). Should-fix: 8 (P-9 to P-16). Notes: 6 (P-17 to P-22).

## Answers to Rex's §12 questions

**Q1 — Is room presence / track metadata itself "collection"?**
Presence is *processing* of session data (who attended, when, that the Observer joined) — and it is already the January model, covered by the January audit record, not by capture consent. It is not biometric collection: joining a room and seeing that a track exists captures no voice characteristic. Two boundaries the design must hold: (a) any SDK-surfaced **audio-level / speaking-indicator** values are derived from media energy — while dormant they must not be sampled, logged, or stored, or "presence" quietly becomes measurement; state this in §3. (b) Track *metadata* (codec, dimensions) is fine to observe for presence; the §2.3 change correctly ensures the SFU never sends the media itself. With (a) stated: presence is outside capture, and the design's treatment is approved.

**Q2 — Incidental interviewer speech in candidate-track audio.**
Yes — it is processing of the interviewer's voice, and "we never subscribed to their track" does not answer it, because the *persisted artefact* contains their speech. It does not block the dormant build (nothing persists). Before activation the design must carry: interviewer notice that candidate audio may incidentally include them; a rule that incidental audio is never *analysed* (no diarization revival); and session-keyed retrievability so an interviewer erasure/DSAR can reach chunks of sessions they sat in (today's candidate-keyed queries cannot). Flag for counsel alongside C-04/C-05 — the interviewer's basis is the employer's, not the candidate's consent, and the design should say whose notice covers it. See P-17.

**Q3 — PUT-first vs registry-row-first.**
**Registry-row-first. Rex's chosen order is not acceptable as written.** The compensating delete handles the *detected* failure; it cannot handle the *silent* one — a crash between PUT and ledger INSERT leaves an object no system can find, and "transiently unregistered" is exactly how permanent orphans describe themselves. The reverse orphan (a PENDING registry row whose object never arrives) is strictly safer: it is visible, countable, reconcilable by a sweeper, and contains no media. The reviewer's required order: commit intent row → PUT → confirm row; sweeper reconciles stale intents; a storage-vs-registry diff test proves zero unregistered objects under kill-injection. See P-3. Rex's worry (rows pointing at nothing) is a data-hygiene issue; the alternative is a privacy breach with no detection path. Hygiene loses.

**Q4 — Ledger encoding (`/api/files/…` reuse).**
Acceptable, with the P-19 condition. Reusing Phase 2 unmodified is the right instinct and the registry row preserves family attribution in the system of record. The risk is operational audit confusion (biometric-adjacent deletions indistinguishable from CV deletions in the ledger's own counts), not correctness. Require family attributability — discriminator or guaranteed join + per-family reporting — and the reuse stands.

**Q5 — DEK creation / no resurrection of a destroyed DEK.**
Reading accepted, evidence required. `getOrCreateDEK` refusing destroyed DEKs, with encrypt-throw → chunk dropped → capture stops, is the correct fail-closed chain *if* the code does what the design says — this programme verifies by test, not by reading, for exactly this class of claim (a resurrected DEK would silently undo an erasure). Add T8b (P-18): post-erasure capture attempt recreates zero DEKs and zero chunks. Also state the concurrent-first-capture note. Subject to that test existing in §8.3, Q5 is answered: no path in §3/§4 as designed recreates a destroyed DEK.

**Q6 — Should measurement rows be DEK-encrypted like the audio?**
**Yes** (P-12). The deciding argument is erasure symmetry: the design's own standard is that destruction must *provably* reach derived copies. Plaintext JSONB measurements survive DEK destruction in the live DB and in backups; encrypted measurements die with the key everywhere the key is gone, which is the only backup story this platform currently has (P-4). The cost is small (one envelope wrap on a per-session JSON blob, no reader to inconvenience). If Rex declines, the design must name the plaintext readers and accept the backup exposure in writing — "nobody reads it yet" is an argument *for* encrypting, not against.

**Q7 — Is retained `pitch_variability` a stress meter in substance?**
Not yet — and the design is what keeps it "not yet." A physical quantity, stored under its physical name, with no norm, no threshold, no reader, no aggregation, and no presentation, is a measurement, not a meter; a meter exists when someone reads a value *as* stress. The substance risk is entirely downstream and entirely foreseeable: the first reader story will be tempted to label it. Constraints to fix **now**, while they cost nothing: (a) the name `pitch_variability` is contractual — any rename toward stress requires the C-05 counsel determination and its own gate; (b) no cross-session aggregation or candidate-level profiling of this field in this design's data model (per-session rows only, 30-day life — both already true; state the prohibition, P-16); (c) Quinn COPY-1 already scans the copy surface. With (a)–(c) stated, retention of the quantity is approved.

**Q8 — Enabling the flag in production for a synthetic session.**
**Yes, that crosses the line the test-environment posture holds — as the design currently stands.** A synthetic participant in a production room proves nothing Quinn's Rung 2 (staging, real LiveKit, dedicated prefix) doesn't prove, while risking everything P-5 identifies: the production worker claims jobs from the production stream, the shared-DB problem is at its worst, a "synthetic" room that a real participant joins becomes real capture under banked consent (P-1), and the artefacts land in the production registry indistinguishable from real ones (P-5). Prohibited until P-2's scope guards and P-5's segregation exist — and even then, unnecessary: Rung 2 staging is the designed ceiling, and production is, per Quinn §8.2, "not a validation rung." State the prohibition in §6.

**Q9 — Does existing `biometric_collection` consent cover capture + 30-day retention?**
**No.** This is P-1 and RL-01. Whatever the S-048 copy said about biometric collection generally, Lex L-ACT-01/02 settles the design requirement: capture-and-retention is a distinct purpose (recorded, stored, retained 30 days, derived-from) that requires its own artefact describing recording in plain words, the derivations, the retention, and withdrawal consequences — obtained fresh, after the activation decision. A gate that cannot distinguish "agreed to presence" from "agreed to be recorded" is a banking mechanism regardless of what the original copy contained. Final sufficiency of the *new* artefact's wording is counsel's (C-04); the *architectural separation* is the design's, and it is currently absent.

**Q10 — Capture finality vs candidate expectation; audit sufficiency.**
No consent principle entitles a candidate to have capture *resume*; the candidate-facing promise runs the other way (capture happens only while every condition holds — finality on failure is the privacy-correct behaviour, and §3.1's one-way transitions are approved). The audit trail, however, is **not yet sufficient**: `error_message` plus in-process capture stats evaporate on restart and live partly in logs. What was/was-not collected for a given session must be reconstructible *per session* after the fact (it is the capture analogue of Lex's January spine). Require a persisted, non-media capture-outcome record per capturing session — counts only: chunks persisted/dropped, gap ratio, stop reason, timestamps — written under the P-7 lock discipline, retained as an accountability record (not on the media schedule). That record is also what makes T5/T6 outcomes auditable in production, not just in tests.

## Verdict — in plain words

**BLOCK CLEARED WITH CONDITIONS.**

The original block was not about dormancy mechanics — those were sound in v1 — it was about the activation path v1 had written down: one env-var flip would have recorded real candidates on January's presence consent, for any employer, with a registration order that could orphan an object no deletion system could ever find, in a shared staging/production database with no environment separation.

v2 rewrites that path rather than patching around it, and the rewrite closes the harms, not just the wording:

- Capture now needs its **own** consent artefact (`observer_capture`), at the **current** version, timestamped **strictly after** the employer's activation enablement — and in this build that artefact does not exist, so the real-candidate path is closed by a missing artefact, not by an operator's promise (P-1).

- Erasure now has a **map**: a 10-row reachability table with a kill mechanism and a maximum lag per copy, including the two honest acceptances (provider replication; Neon PITR expiry + re-erasure after any restore) stated in §5 for Lex/Sumanth to accept knowingly (P-4).

- **Test-scope machinery (`is_test`, test prefix, capture-outcome record).** Checked specifically for a path where `is_test` data reaches candidate-facing surfaces: storage is prefix-separated (`observer-audio-test/` never mixes with `observer-audio/`); rows are marked on all three tables; §3.4 states the filter rule for every future candidate-facing and real-data erasure/retention view (`is_test = false`), states that no such surface reads this data in this build at all, and classes any cross-contamination as an incident (L-DOR-05).
