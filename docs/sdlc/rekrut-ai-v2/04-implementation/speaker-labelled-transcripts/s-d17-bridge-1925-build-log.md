## What was built

1. **Migration 298** (`migrations/298_event_session_bridge.js`) — expand-only, exactly per design §3: `interview_events.interview_session_id INTEGER NULL REFERENCES interview_sessions(id) ON DELETE SET NULL` + index `idx_interview_events_session`; `governing_session_id` + `consent_receipt_id` plain-integer (no FK) provenance columns on `diarization_jobs` and `diarization_runs`. No change to the migration-130 XOR, no `consent_receipts` change, no backfill. Post-state assertions in the migration-296 pattern. **Local rig only — not executed on Neon/shared DB** (post-Nov-1 promotion order).
2. **Governing-session creation** (`lib/governingSession.js`, new) — creation only, never adoption: returns an existing link untouched; otherwise creates the session via the existing `SessionService.create` (`type:'human'`, `config:{biometric_collection:false}` — refused by default) and links it with a guarded UPDATE (a lost race re-reads the winner, never overwrites). `SessionService.create` gained an optional executor parameter (defaults to the shared pool; every pre-existing caller unaffected) so event creation enlists it in the caller's transaction.
   - At event creation: `routes/interview-events.js` POST now runs event insert + governing-session creation + proposed slots in **one transaction** (BEGIN…COMMIT on one client).
   - Legacy events: lazy creation at event room creation (`server/routes/livekit.js` POST `/api/livekit/rooms`), non-blocking — a failure leaves the event unbridged and the gate blocks it fail-closed.
3. **Consent capture (design §4.4)** — `POST /api/interviews/:id/biometric-consent`: candidate-authenticated, event's own candidate only, S-011 ownership assertion on the governing session, then `consentService.recordConsent` against the governing session — which performs the existing S-070 propagation itself (grant flips `config.biometric_collection=true`; decline records the never-granted receipt and leaves it false). Unbridged event → `409 NO_GOVERNING_SESSION`, nothing recorded. The current text the candidate reads is the existing `GET /api/consent/texts/biometric` (v1.2+).
   - **GAP (explicit, per STOP 1):** the join-screen **UI surface** presenting this capture in the client is a materially larger client build than the gate contract and is NOT in this PR. The server-side endpoint/contract is built and tested; no UI was invented and the capture was not silently skipped. Quinn's grant/decline candidate journey (design §7) needs that surface — it remains open work after this PR, recorded here and in the PR body.
4. **Gate bridge** (`lib/diarizationGate.js`) — session-linked path behaviour-identical; event-linked path implements design §5 steps 1–7 exactly: `NO_GOVERNING_SESSION` (unbridged / governing row gone), `SESSION_BINDING_MISMATCH` (candidate/application/job-application binding, server-derived ids only, consent never consulted on mismatch), consent states mapped via the existing `checkConsentState` on the governing session only, temporal precedence from the governing receipt row (`granted_at <= recordings.started_at`; late grant → `CONSENT_AFTER_RECORDING`; missing `started_at` → `CONSENT_UNVERIFIABLE`), then `canEnableObserver(governing)`. Allow returns `via:'event_bridge'` + `consentReceiptId`. Header deviation note updated: the #1906 SCHEMA NOTE is now recorded **CLOSED by #1925**.
5. **Provenance + write-time comparison** (`workers/diarization/index.js`, `lib/transcriptStitch.js`) — at claim, bridge jobs persist `governing_session_id` + `consent_receipt_id` on the job row; at write, the re-resolved governing session is compared against claim-time (a change cancels `consent_blocked_at_write:SESSION_BINDING_MISMATCH`, output discarded); `persistStitch` writes both ids onto the `diarization_runs` row. Session-linked jobs call the stitch with exactly the pre-bridge argument shape.

## Specialist reviews

- **ecc/database-reviewer — MANDATORY pass on migration 298: APPROVE-WITH-CONDITIONS; all three conditions implemented in this PR.** (1) Post-state assertions verify the FK itself, by column, with its delete rule (`confdeltype='n'` = SET NULL, via `pg_constraint`+`pg_attribute`), keyed by (table, column) pair with nullability — because `ADD COLUMN IF NOT EXISTS` would silently skip the `REFERENCES` if the column pre-existed without it; an additional assertion locks in *no* FK on the provenance columns. (2) The bridge index is partial (`WHERE interview_session_id IS NOT NULL`) — it exists for the FK's SET NULL fan-out on session deletes (migration-126 partial-index precedent), and the FK lookup implies the predicate. (3) The migration header records, in the 296 deviation style, why the provenance columns carry no FK (CASCADE would erase the record, SET NULL would falsify it, RESTRICT would block lawful deletion — cf. migration 245) and that no index on them is deliberate (no query path filters by them). On the review questions: no `NOT VALID`/`ADD CONSTRAINT` split is needed (a brand-new column is NULL in every row — validation is trivial, no table rewrite; house precedent migration 129); `SET NULL` is correct over CASCADE (which would chain into recordings/slots) and RESTRICT (which would block erasure); plain-integer provenance is sound and precedented (migration 129); `down()` no-op matches the shared-DB rule. Full report in the PR's Specialist Reviews section. The reviewer's forward note — S-D17's bundle should carry the real-DB run on the fresh rig — is already satisfied for the build itself (fresh migrate incl. 298 + integration, below).
