# S-D11 Build Log — Candidate-view parity

**Story:** S-D11 (#1913) · **Epic:** #1900 · **Design:** Architecture §3.8, §5.1 · **PRD:** §7 decision, FR-D13, FR-D19 · **Gate:** synthetic fixtures + local rig only; no real recordings until S-D17 enablement; `DIARIZATION_ENABLED` untouched.

## What was built

The candidate-facing half of "one artefact, two readers" (JT-D5). The API already served the owning candidate the identical composed transcript (S-D09 composition is server-side; `canAccessRecording` already grants the candidate detail/playback/transcript) — but the only transcript UI sat behind `RecruiterGuard`, so a candidate had **no surface at all**. This story adds the surface and the candidate branch; it changes no server code and no permission.

- **Candidate route** — `recordings/:id/playback` nested under `/candidate` in `client/src/App.tsx` (inside `DashboardLayout`), element `Protected > CandidateGuard > RecordingPlaybackPage`. `CandidateGuard` (new, beside `RecruiterGuard`) admits candidate-role users only and redirects everyone else to their own dashboard. It is UX only — the server remains the sole authority: an admitted-but-non-owning candidate still gets the API's 403 and the page's existing not-found state. The recruiter routes and the bare-`Protected` recruiter-spine playback route are untouched. The page component is the recruiter's own — no second rendering implementation to diverge.
- **Raise-it route (AC-2)** — in the estimate-note block, exactly where a recruiter sees "Correct speaker names", a non-recruiter viewer of a `complete` recording sees the static text: *"If a speaker name looks wrong, raise it with the hiring team."* Plain text by design (privacy condition): no link, no mailto, no form, nothing carrying the recording id. The editor is never fetched or rendered for non-recruiters (the S-D10 `editorEligible` gate already ensured this; the story's tests now pin it for the candidate role).
- **Consent names only (privacy condition)** — the Recording Consent badges rendered `name || email` for every viewer; a nameless consenter's email would have rendered to the candidate, beyond PRD §7's "names shown in the call". Non-recruiter viewers now render `name || 'Participant'`; the recruiter view is byte-unchanged.
- **Back link (privacy condition)** — the not-found state's "Back to Recordings" action pointed at `/recruiter/recordings` for everyone; it now branches (`isRecruiter ? '/recruiter/recordings' : '/candidate/interviews'`).

Nothing else changes (AC-3): the speaker-names section renders the same read-only composed-label list for candidates as for non-corrector recruiters; no scores, no integrity content, and no interviewer data beyond the call names were added anywhere — the candidate's API payloads are asserted free of `recruiter_notes`, segment `highlights`, and every mapping-internal key (`participant_user_id`, `sample_turn`, `participants`).
